# MyOS — Data Model

Sections **1–11 are implemented**: they are the schema produced by
`backend/alembic/versions/0001_phase_1_initial_schema.py` plus
`0002_goal_project_link.py` and mapped by `backend/app/models/*`.

Sections **12–17 are specification only** — no migration creates those tables yet, and no Phase 1 endpoint reads or writes them. They exist so Phases 2–6
can be built without redesigning the parts that already work.

Ground truth for Phase 1, in this order of reliability:

1. `backend/app/models/*.py` (SQLAlchemy 2.0 `Mapped[...]` declarations)
2. `python3 -m alembic upgrade head` on an empty file, then `.schema` in `sqlite3`
3. this document

---

## 1. Conventions every table follows

| Rule | How it is enforced |
|---|---|
| Primary keys are UUID4 **strings** generated by the server | `ID_COLUMN = sa.String(36)`, `default=new_id` (`app/core/utils.py`). A client-supplied `id` in a request body is rejected with 422 (`extra="forbid"`). |
| Every business table is owned by one workspace | `workspace_id VARCHAR(36) NOT NULL` + `FOREIGN KEY … ON DELETE CASCADE`, always indexed. Services filter on it before anything else. |
| `created_at` / `updated_at` on every table | `TimestampMixin` — `DATETIME` (tz-aware UTC in Python), `default=now_utc`, `onupdate=now_utc`. API.md response rule 3 depends on `updated_at` for "recent activity" ordering. |
| Row origin | `SourceMixin.source VARCHAR(16) NOT NULL DEFAULT 'user'`, CHECK in `('user','demo','import','ai')`. Only `demo` rows are wiped by `POST /demo/reset`; `import` is used by `POST /tasks/import`. |
| Enumerations are checked in the database *and* in Pydantic | `enum_check(column, "<enum key>")` builds `ck_<table>_<column>` from `ENUMS` in `app/models/enums.py`, the same mapping `GET /meta` returns and API.md lists. |
| Numeric ranges | `range_check` → `ck_<column>_range` (`BETWEEN 0 AND 100` for progress columns); `non_negative` → `ck_<column>_non_negative` for minutes and position. |
| Defaults live in Python, not in the DDL | The generated `CREATE TABLE` has no `DEFAULT` clause; ORM insert always supplies the value. A future bulk-import phase must therefore insert through the services (or set the columns explicitly). |
| Money and rates are `Numeric`, never floats | `sa.Numeric(precision, scale)` everywhere in Phases 3–5 so PostgreSQL needs no change. |
| Anything JSON is a real JSON column | `sa.JSON` (`activity_logs.payload`); the engine serialises it with the same encoder the API uses (`json_serializer=zjson.dumps`), so dates/`Decimal`/enum members inside a payload round-trip. |
| Timestamps in JSON end with `Z` | `app/core/json.py` formats every `datetime` as UTC `…Z`; dates are `YYYY-MM-DD` or `null`. |

`alembic_version` (one `VARCHAR(32)` row) is created and maintained by Alembic, not by the
models, and is excluded from `GET /export`.

### `task_dependencies`

| column | type | null | notes |
|---|---|---|---|
| `id` | `VARCHAR(36)` | no | PK |
| `task_id` | `VARCHAR(36)` | no | FK → `tasks` CASCADE |
| `depends_on_task_id` | `VARCHAR(36)` | no | FK → `tasks` CASCADE |

### `tags`, `task_tags`, `note_tags`, `contact_tags`

`tags`: `id`, `workspace_id` (FK CASCADE), `name VARCHAR(64)`, timestamps,
`UNIQUE (workspace_id, name)`. The name keeps its typed casing (`"CRM"` ≠ `"crm"` for
display); uniqueness and filtering ignore case and surrounding spaces, which is a service
rule, not a collation trick — so it behaves identically on PostgreSQL.

Each association table is `(entity_id, tag_id)` with a composite PK, both FKs CASCADE, and an
index on `tag_id`. No `created_at`: the tag list is a set, and ordering is defined by the
parent's own ordering.

|---|---|---|---|
| `id` | `VARCHAR(36)` | no | PK |

### `note_relations`

Polymorphic link from a note to any indexable object.

| column | type | null | notes |
|---|---|---|---|
| `id` | `VARCHAR(36)` | no | PK |
| `workspace_id` | `VARCHAR(36)` | no | FK CASCADE |
| `note_id` | `VARCHAR(36)` | no | FK → `notes` CASCADE |
| `target_type` | `VARCHAR(24)` | no | CHECK `task/note/project/milestone/contact/company/goal` |
| `target_id` | `VARCHAR(36)` | no | **no FK**: the target may be deleted while the note stays |
| `label` | `VARCHAR(64)` | yes | optional chip text |
| `created_by` | `VARCHAR(36)` | yes | user id, reserved for multi-user |
| `created_at`, `updated_at` | `DATETIME` | no | |

`UNIQUE (note_id, target_type, target_id)` (`note_target`) plus index
`(target_type, target_id)` for backlinks. Creating a duplicate — including one that differs
only by case, or one that is still pending inside the same batch — is skipped rather than
raising, because a note's relations are a set. `GET /notes/{id}` hides links whose target no
longer exists; the row itself survives and still appears in `/export`.

## 6. Outcomes and signals

### `goals`
`id`, `workspace_id`, `project_id VARCHAR(36)` (FK `projects.id` **ON DELETE SET NULL**,
indexed, nullable — added by revision `0002`), `title VARCHAR(200) NOT NULL`,
`description TEXT`, `category VARCHAR(64)`,
`priority VARCHAR(12)` (CHECK `priority`), `status VARCHAR(16)` (CHECK
`active/completed/abandoned`), `progress INTEGER` (CHECK 0..100, default 0), `target_date DATE`,
`completed_at DATETIME`, timestamps, `source`.
Indexes: `(workspace_id, status)`, `(workspace_id, target_date)`, `(project_id)`.

A goal serves at most one project and is not part of its work breakdown: deleting the project
detaches the goal (`project_id → null`) instead of deleting or completing it, exactly like
`tasks.project_id`. The API therefore returns the same two fields a task does — `project_id`
and the trimmed `project` object `{id, name, status}` — and `POST /goals` / `PATCH /goals/{id}`
take an optional `project_id`: an id that does not exist in this workspace is a 422
`project_id not found` (the task rule, `crud.validate_fk`), `null` clears the link.

### `notifications`

| column | type | null | notes |
|---|---|---|---|
| `id` | `VARCHAR(36)` | no | PK |
| `workspace_id` | `VARCHAR(36)` | no | FK CASCADE |
| `kind` | `VARCHAR(32)` | no | CHECK `notification.kind` |
| `severity` | `VARCHAR(12)` | no | CHECK `info/warning/critical` |
| `title` | `VARCHAR(200)` | no | |
| `body` | `TEXT` | yes | |
| `entity_type`, `entity_id` | | yes | soft reference to the cause |
| `href` | `VARCHAR(300)` | yes | in-app link, e.g. `/tasks?filter=overdue` (§6 "Deep links") |
| `read` | `BOOLEAN` | no | default `false` |
| `read_at`, `resolved_at` | `DATETIME` | yes | `resolved_at` is set when the underlying condition clears |

| `created_at`, `updated_at` | `DATETIME` | no | |

Index `(workspace_id, read, created_at)` serves the unread list; `(workspace_id, kind)` and
`(entity_type, entity_id)` serve the filters. Keys look like `task_overdue:<task id>`,
`task_due:<task id>:<date>`, `milestone:<milestone id>`, `reminder:<reminder id>`,
`project_stalled:<project id>:<week>`; the last component is what lets a *new* occurrence of
the same condition create a fresh row. Notifications are derived data: `GET` never creates
them, `POST /notifications/refresh` (or `app.cli notify`) does, and `demo.reset` clears all
rows for the workspace and rebuilds them.

| column | type | null | notes |

Indexes: `(workspace_id, created_at)`, `(workspace_id, project_id)`,
`(entity_type, entity_id)`. Every mutating endpoint writes one row in the same transaction as
the change (ARCHITECTURE.md §3). Timestamps are second-precision
(`now_utc()` drops microseconds), so same-second rows are ordered by `id desc` — deterministic,
not chronological.

### Deep links: the `href` contract

`activity_logs.href`, `notifications.href`, `dashboard.insights[].href` and
`search.groups[].items[].href` are all produced by one function —
`app/services/links.py::href_for(entity_type, entity_id, project_id=None)` — because a stored
href that points at a route the UI does not have is a broken link no error page will ever show.
Nothing else in `backend/app` builds a link by hand; the seeder calls the same helper, and the
route names live in module constants (`links.TASKS`, `links.PROJECTS`, …).

The screens are the app's canonical routes (no prefix, no router group), so these are the only
targets the backend may emit:

| entity type | href | why |
|---|---|---|
| `task` | `/tasks?task=<id>` | the tasks screen selects a row by query parameter |
| `note` | `/notes?note=<id>` | same, on the knowledge hub |
| `contact` | `/contacts?contact=<id>` | people directory (companies included) |
| `company` | `/contacts` | companies have no page of their own; the people page lists them |
| `project` | `/projects/<id>` | the only detail route the UI has |
| `milestone` | `/projects/<project_id>` | a milestone is a section of its project, never its own page |
| `milestone` with no project | `/projects` | the guard: a missing `project_id` must not become `/projects/None` |
| `goal` | `/goals` | goals have their own screen — not `/settings?tab=goals` |
| `reminder`, `notification` | `/notifications` | that page lists both |
| `workspace` | `/settings` | where a workspace is managed |
| `activity` | `/activity` | |
| anything unknown | *(no href at all)* | `href_for` returns `None`; a link is worse than no link |

Two more shapes exist, and they are the only ones outside the entity table:

* saved views of the task list — `/tasks?filter=overdue` (the shape API.md shows in its
  notification example), `/tasks?filter=today`, `/tasks?filter=week`;
* a search *group* header — `links.search_href(group, term)` gives that group's list page plus
  `?q=<term>` (`/tasks?q=order`, and `/contacts?q=…` for the companies group, which has no page
  of its own) while the *items* inside it use the entity links above.

Goals have their own screen, so a goal insight never points at a settings tab.
`tests/test_links.py` asserts every mapping above, the missing-project case, that no emitted href
contains the literal string `None`, and that no emitted href starts with the retired screen
prefix — a prefix reappearing anywhere in an href fails the suite.

Changing a route is a one-line edit in `links.py`, plus that test file; the column stays a
snapshot of the link as it was when the row was written (see §7), which is why the helper must
be right the day the row is created.

## 7. Values the API returns but the database does not store

| API field | Rule (all in `app/services/`) |
|---|---|
| `project.progress`, `project.task_counts` | `stats.aggregate`: `100` when status is `completed`/`archived`, else `(200 * done + total) // (2 * total)` when the project has tasks, else `manual_progress`. 8 done of 13 ⇒ `62`. |
| `project.next_due` | nearest **future** open task (`due_date > today`), `{title, due_date}` or `null`. |
| `task.project` / `task.project_id` | `project` is the joined `{id, name, status}` object. |
| `goal.project` / `goal.project_id` | the same trimmed object and the same rule — `goal.project_id` *is* stored (§6), only the object is derived. |
| `task.tags` | `tags` rows through `task_tags`, ordered by name. |
| `task.is_overdue`, `task.is_due_today` | `due_date < today` and `due_date == today`, with `status` in the open set `todo/in_progress/blocked`. |
| `task.children` | subtasks of the same workspace, `position` order. |
| `note.excerpt` | first 160 characters of `content`, `…` appended when truncated. |
| `note.categories` (list envelope) | `{category: count}` over the filtered set, not the whole workspace. |
| `milestone.days_away` | `(date - today).days`, negative when past. |
| `dashboard.*`, `insights` | recomputed per request; nothing cached. |
| `notification.href`, `body` | generated by the rule that created the row and stored, so the badge cannot change under the user's feet; the href itself comes from `links.href_for` (§6, "Deep links"). |
| `meta.counts` | live `COUNT(*)` + `stats` aggregates. |

## 8. Delete behaviour at a glance

| Parent removed | Children deleted (CASCADE) | Children detached (SET NULL) | Untouched |
|---|---|---|---|
| `workspaces` | every row in this document | — | — |
| `projects` | `milestones` | `tasks.project_id`, `notes.project_id`, `goals.project_id` | `activity_logs`, `tags`, `notes` content |
| `tasks` | `task_tags`, `task_dependencies` | `parent_task_id` of its subtasks | `activity_logs`, `notifications` (resolved on the next refresh), `note_relations` rows that pointed at it — kept, and rendered without a title |
| `notes` | `note_tags`, `note_relations` | — | backlinks of other notes (rendered without a title) |
| `companies` | — | `contacts.company_id` | `contacts` themselves |
| `contacts` | `contact_tags` | — | `note_relations` rows |
| `tags` | all three association rows | — | — |

| `member.role` | `owner, admin, member, viewer` |
| `source` | `user, demo, import, ai` |
| `note_relation.target_type` | `task, note, project, milestone, contact, company, goal` |

## 10. Index strategy, and why

Every index exists because a Phase 1 query needs it — the leading column is always
`workspace_id` for business tables because tenancy is applied first:

* due-date and status windows (`GET /tasks?due=overdue|today|week|upcoming`) →
  `(workspace_id, due_date)`, `(workspace_id, status)`.
* kanban and project detail → `(project_id, position)`, `(project_id, status)`.
* the knowledge hub's category chips → `(workspace_id, category)`.
* unread notifications, ordered newest first → `(workspace_id, read, created_at)`.
* backlinks, which ask the opposite question (`who references this id`) →
  `(target_type, target_id)` and `(entity_type, entity_id)`.
* `/demo/reset` and `source=import` filters → `source`.
* the two "which project?" lookups the settings and project screens make → `tasks.project_id`,
  `goals.project_id` (both `SET NULL`, so the index also serves "unlinked").

`GET /search` uses `LIKE '%term%'` on a handful of columns. On SQLite with a personal dataset
that is fast enough and honest; if it ever hurts, the fix is a `sqlite-fts5` index (or
`pg_trgm`), not a schema change — which is why no full-text column is faked today.

## 11. Moving to PostgreSQL

SQLAlchemy 2.0 typed models only, no SQLite-specific types:

| Phase 1 type | Postgres |
|---|---|
| `String(36)` PK (UUID4 text) | works as-is; `UUID` is the alternative if ids are ever generated by the DB |
| `DateTime(timezone=True)` | `TIMESTAMPTZ` — values are already tz-aware UTC |
| `Date` | `DATE` |
| `Text`, `String(n)` | `TEXT`, `VARCHAR(n)` |
| `Boolean`, `Integer` | `BOOLEAN`, `INTEGER` |
| `Numeric(p, s)` (Phases 3–5) | `NUMERIC(p, s)` |
| `JSON` | `JSONB` (SQLAlchemy maps it) |
| CHECK enum constraints | unchanged |

Two operational differences: the per-connection `PRAGMA` listener in `app/core/db.py` is
SQLite-only and simply does not fire elsewhere, and WAL/busy-timeout tuning disappears.
`alembic upgrade head` runs the same revision; Phase 1's DDL is portable, so a Postgres
install needs a connection string, not a migration rewrite.

## 13. Phase 3 — Finance

Money is `NUMERIC(14,2)`, rates are `NUMERIC(18,6)`, always with an explicit `currency
VARCHAR(8)` on the row; `workspaces.currency` is only the default for new rows. Nothing is ever
converted silently: a converted figure is stored next to the original, never in place.

### `income_profiles`
One row per profile a scenario can model (`freelance`, `salary`, `mixed`): `id`,
`workspace_id`, `name VARCHAR(120)` NOT NULL, `kind VARCHAR(24)` CHECK
`salary, freelance, contract, business, mixed`, `gross_monthly NUMERIC(14,2)`,
`currency VARCHAR(8)` NOT NULL, `tax_regime VARCHAR(24)` CHECK `none, flat, slab, presumptive`,
`tax_rate NUMERIC(5,2)` CHECK `0..100`, `slabs JSON` (nullable, `[{up_to, rate}]`),
`notes TEXT`, timestamps, `source`. `UNIQUE (workspace_id, name)`.

### `exchange_rates`
`id`, `workspace_id`, `base VARCHAR(8)` NOT NULL, `quote VARCHAR(8)` NOT NULL, `rate
NUMERIC(18,6)` NOT NULL CHECK `> 0`, `as_of DATE` NOT NULL, `provider VARCHAR(24)`,
timestamps. `UNIQUE (workspace_id, base, quote, as_of)`; lookups pick `MAX(as_of) <= date`,
so a missing day degrades to the last known rate instead of inventing one.

### `services`
The catalogue of what can be sold: `id`, `workspace_id`, `name VARCHAR(160)`, `code VARCHAR(32)`
(`UNIQUE (workspace_id, code)`), `description TEXT`, `unit VARCHAR(16)` CHECK
`hour, day, fixed, retainer, seat`, `default_price NUMERIC(14,2)`, `currency VARCHAR(8)`,
`active BOOLEAN` default true, `project_template JSON` (nullable — the task breakdown to clone
when it is sold), timestamps, `source`.

### `service_plans`
Named packages over `services`: `id`, `workspace_id`, `service_id` (FK → `services` **CASCADE**),
`name VARCHAR(160)` NOT NULL, `interval VARCHAR(16)` CHECK `monthly, quarterly, yearly, one_time`,
`price NUMERIC(14,2)` NOT NULL CHECK `>= 0`, `currency VARCHAR(8)`, `included_units NUMERIC(8,2)`,
`overage_rate NUMERIC(14,2)`, `trial_days INTEGER` CHECK `0..90`, `active BOOLEAN`, timestamps,
`source`. Index `(workspace_id, service_id, interval)`.

### `subscriptions`
`id`, `workspace_id`, `plan_id` (FK → `service_plans` SET NULL — history must outlive a retired
plan), `client_id` (FK → `clients` SET NULL), `company_id` (FK SET NULL), `status VARCHAR(16)`
CHECK `trialing, active, paused, cancelled, expired`, `started_on DATE` NOT NULL, `renews_on DATE`,
`cancelled_on DATE`, `price NUMERIC(14,2)` NOT NULL, `currency VARCHAR(8)`, `interval VARCHAR(16)`,
`invoice_number VARCHAR(40)`, `notes TEXT`, timestamps, `source`.
Index `(workspace_id, status, renews_on)` — the "what renews this month" query.

### `expense_categories`
Tree of spending buckets: `id`, `workspace_id`, `name VARCHAR(120)` NOT NULL,
`parent_id` (self FK → `expense_categories` **CASCADE**), `kind VARCHAR(16)` CHECK
`fixed, variable, one_off, tax`, `system_key VARCHAR(48)` (stable key for seeded rows:
`rent`, `software`, `insurance`… so presets are idempotent), `color VARCHAR(16)`, `archived BOOLEAN`,
timestamps. `UNIQUE (workspace_id, name, parent_id)`; a CHECK `parent_id <> id`.

### `expenses`
`id`, `workspace_id`, `category_id` (FK → `expense_categories` **SET NULL**), `label VARCHAR(200)`
NOT NULL, `amount NUMERIC(14,2)` NOT NULL CHECK `>= 0`, `currency VARCHAR(8)` NOT NULL,
`paid_on DATE` NOT NULL, `recurring BOOLEAN` default false, `recurrence VARCHAR(16)` CHECK

### `income_transactions`
Every inflow, invoiced or not: `id`, `workspace_id`, `client_id` (FK SET NULL),

## 14. Phase 4 — Integrations

`calendar_connections` and `calendar_events` are specified in §12 (they arrive with CRM
because that is where they are needed). The rest of the module is the credential and

### `integrations` (system)
One row per provider the install knows about: `id`, `workspace_id`, `provider VARCHAR(32)` NOT

`scopes VARCHAR(300)`, `capabilities JSON` (`{"import": ["events"], "export": []}`),

### `data_connections` (business)
The non-calendar, mostly read-only feeds (bank export, Stripe, a CSV upload): `id`,
`workspace_id`, `integration_id` (FK → `integrations` SET NULL), `name VARCHAR(140)`,
`kind VARCHAR(24)` CHECK `csv_upload, api_pull, webhook_push, database_view`, `direction VARCHAR(8)`
CHECK `import, export`, `target_table VARCHAR(48)` (`expenses`, `income_transactions`, …) —

### `integration_runs`
Supporting table for the two above, so "what happened on the last sync" is answerable without
a log parser: `id`, `workspace_id`, `connection_id` (FK **CASCADE**), `started_at DATETIME`,
`finished_at DATETIME`, `status VARCHAR(16)` CHECK `running, success, partial, failed`,
`rows_created INTEGER` CHECK `>= 0`, `rows_updated INTEGER` CHECK `>= 0`, `rows_rejected INTEGER`
CHECK `>= 0`, `errors JSON`, timestamps. Index `(connection_id, started_at)`. The idempotency
contract is the one `POST /tasks/import` already demonstrates: a re-run of the same payload
creates nothing twice, because each row carries a stable external key.

## 16. Phase 6 — AI automation

No new tables in the first cut: `assistant.py` calls the same services the UI does, so every
action is already audited in `activity_logs` with `source = 'ai'` on the rows it writes
(`source` is CHECK-constrained for exactly this reason). When the phase needs a transcript
store, it will be `assistant_runs`
(`id`, `workspace_id`, `prompt JSON`, `plan JSON`, `status CHECK pending/confirmed/rejected/done`,
`created_at`) and will follow §1 like everything else. Confirmation is a requirement of
ARCHITECTURE.md §5 ("consequential actions require an explicit confirmation step"), which is
why nothing AI-related lands before Phase 6.

## 17. Migration plan

| revision | phase | contents |
|---|---|---|
| `0001` | 1 (built) | the 19 tables of §2–§6 + `alembic_version`; works on an empty SQLite file |
| `0002` | 1 (built) | `goals.project_id` — one nullable column, its `SET NULL` FK and its index, via `op.batch_alter_table`; no row is rewritten and `0001` is untouched |
| `00xx` | 2 | `job_applications`, `job_interviews`, `leads`, `clients`, `meetings`, `client_tags` |
| `00xx` | 3 | `income_profiles`, `exchange_rates`, `services`, `service_plans`, `subscriptions`, `expense_categories`, `expenses`, `income_transactions`, `cost_scenarios`, `cost_scenario_items` |
| `00xx` | 4 | `integrations`, `data_connections`, `integration_runs`, `calendar_connections`, `calendar_events` |
| `00xx` | 5 | `businesses`, `products`, `analytics_metrics`, `reviews` |
| `00xx` | 6 | `assistant_runs` (only if the assistant needs it) |

Each phase ships as **one** revision adding its own tables, never editing an earlier one.
Schema changes to Phase 1 tables are additive only — `0002` is the pattern: a new nullable
column, its index and its FK, built with `op.batch_alter_table` so the same code rebuilds the
table on SQLite and emits a plain `ALTER` on PostgreSQL. No Phase 1 column is ever narrowed or
repurposed, and a phase that needs a new enum value adds a CHECK with a new name instead of
mutating `ck_tasks_status` (SQLite cannot `ALTER CONSTRAINT`).

Every phase also has to keep four things true, because the UI already assumes them:
`GET /export` includes the new tables in `TABLE_ORDER`; `GET /meta` serves their enums; a
`GET` never mutates; and `demo.seed` can generate (and `demo.reset` can remove) rows for the
new module with `source = 'demo'`.
